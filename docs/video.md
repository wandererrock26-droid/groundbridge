# Видео: захват FPV и ретрансляция по RTSP

## Как это устроено

```
Аналоговый FPV-приёмник → USB-плата захвата (UVC, /dev/videoN) ─┐
                                                                ├─► ffmpeg ─► MediaMTX ─► rtsp://<IP>:8554/live
IP-камера (RTSP, по сети/USB-Ethernet) ─────────────────────────┘
```

Источник (плата захвата или RTSP-камера) выбирается в панели — **выходная
ссылка при этом не меняется**: зрители (VLC/QGroundControl/Mission Planner)
всегда подключаются к `rtsp://<IP_Pi>:8554/live`.

`install.sh` ставит ffmpeg, v4l-utils и MediaMTX (systemd-сервис `mediamtx`,
RTSP-порт 8554). Управление захватом — вкладка «Видео» панели.

## Тестовая заглушка

Если настроенный источник недоступен, на тот же адрес автоматически
публикуется статичная картинка «КАМЕРА НЕ ОБНАРУЖЕНА» с живыми датой и
временем. Как только камера появляется — заглушка сама уступает место
реальному потоку (и наоборот). Работает при включённом автозапуске
(`video.autostart: true`) и не мешает ручному «Остановить».

**Защита от зацикливания**: если путь формально существует, но ffmpeg
падает на нём раз за разом (на Pi 5 часть `/dev/videoN` — служебные узлы
ISP/кодека RP1, а не платы захвата; проверь `v4l2-ctl --list-devices`) —
после 3 неудач подряд попытки приостанавливаются на ~60 секунд, показывается
заглушка. Смена источника в панели сбрасывает счётчик сразу.

## Источник: RTSP-камера

Вкладка «Видео» → «Источник видео» → **RTSP-камера**, впиши ссылку
(`rtsp://192.168.1.50:554/stream1` — путь зависит от модели). Пока выбран
этот источник, плата захвата физически не открывается.

## Проброс без обработки — режим по умолчанию для RTSP-камеры

Галочка **«Проброс без обработки»** убирает станцию из видеотракта целиком.
Поток к камере поднимает сам MediaMTX, а ffmpeg не запускается вовсе:
разрешение, частота кадров, кодек и расстановка ключевых кадров остаются
такими, какими их отдала камера. Настройки разрешения, битрейта и кодека в
этом режиме не применяются — применять их не к чему.

Почему так. На апробации танка та же камера, воткнутая в меш напрямую, шла
ровно, а через станцию с `-c copy` начинала подтормаживать и «троить».
Перепаковка формально ничего не пересчитывает, но всё равно означает лишний
процесс, лишний буфер и лишнюю точку, где кадры могут подождать. Разница
видна не в цифрах, а на скорости: оператор ведёт машину по картинке, и
полсекунды задержки — это метры.

Технически станция один раз говорит MediaMTX через его локальный API
(`127.0.0.1:9997`), какую камеру раздавать:

```
POST /v3/config/paths/add/live
{"source": "rtsp://192.168.100.10:554/stream",
 "sourceOnDemand": false, "rtspTransport": "tcp"}
```

`sourceOnDemand: false` — поток держится постоянно, чтобы первый зритель не
ждал подключения к камере в момент выезда. `rtspTransport: tcp` — по UDP
через меш кадры сыплются.

Ссылка для оператора не меняется: та же `rtsp://<станция>:8554/live`.
В панели статус показывается как «проброс без обработки», а счётчики
кадров и битрейта стоят прочерком — их считал ffmpeg, которого теперь нет.

Проброс выключается сам в двух случаях, и панель об этом прямо пишет:

- **задан текст OSD** — надпись поверх картинки требует перекодирования, то
  есть ровно того, от чего мы уходим. Очисти поле OSD, чтобы вернуть проброс;
- **MediaMTX не отвечает по локальному API** — настраивать проброс нечем.
  Обычно это старый `mediamtx.yml` без `api: yes`; лечится повторным
  запуском `./install.sh`, который дописывает эту строку.

В обоих случаях поток продолжает идти через станцию — картинка не пропадает,
но нагрузка и задержка возвращаются.

Если проброс снять галочкой, станция освобождает путь в MediaMTX и снова
публикует туда ffmpeg. Для этой схемы у RTSP-камеры есть кодек **copy** —
ретрансляция без перекодирования, почти нулевая нагрузка на CPU. Она нужна
там, где проброс невозможен: например, когда обязателен OSD.

## Аппаратное кодирование: у каждой платы по-своему

Сейчас станция кодирует программно на всех платах. У Pi 4 аппаратный
H.264 есть (`h264_v4l2m2m`), у ROCK 5C свой (Rockchip MPP), у Pi 5 нет
вовсе. Подробности — в [boards.md](boards.md).

На Pi 5 кодирование программное (libx264/libx265) и
делит CPU с мостом управления. Поэтому по умолчанию `ultrafast` +
`tune=zerolatency`. Если видео дёргается — снизь разрешение (720×480) или
битрейт, либо переключись на **MJPEG** (без перекодирования, почти не грузит
CPU, но выше битрейт).

## OSD — имя оператора на видео

Поле «Имя оператора» накладывает текст по центру кадра через ffmpeg
`drawtext` — виден во всех плеерах, не только в браузере. Работает в
H.264/H.265 (в MJPEG/copy перекодирования нет — наложить нельзя).
«Обновить OSD» применяется мгновенно, без перезапуска потока. Нужен пакет
`fonts-dejavu-core` (ставится install.sh).

## Просмотр

- **В панели**: встроенный плеер WebRTC (задержка ~секунда, лучший для FPV)
  или HLS (выше задержка, шире совместимость). Порты 8888/8889/8189 уже
  открываются install.sh при активном ufw.
- **VLC / QGroundControl / OBS**: RTSP-ссылка из панели (кнопка
  «Копировать») как сетевой поток.
- **Mission Planner**: MP требует полноценный GStreamer-pipeline — панель
  строит его автоматически (поле «GStreamer pipeline», подстраивается под
  кодек). На компьютере с MP должен стоять **GStreamer runtime**
  (MSVC + development, оба 64-bit, [gstreamer.freedesktop.org](https://gstreamer.freedesktop.org/download/)).
  В MP: Flight Data → правой кнопкой на видео → Video Source → GStreamer →
  вставить строку целиком. Если картинка «мигает белым/цветными блоками» в
  MP, а в VLC цела — это особенность декодера GStreamer на Windows; иногда
  помогает переключение на H.265.

## Сохранение настроек

Разрешение/битрейт/кодек/пресет/устройство/OSD, изменённые из панели,
хранятся в `data/video_state.json` и переживают перезапуск. `config.yaml`
задаёт только значения по умолчанию на самый первый запуск.

## Диагностика

```bash
sudo systemctl status mediamtx
sudo journalctl -u mediamtx -f
sudo journalctl -u roverlink -f   # здесь же логи ffmpeg
```

Частые проблемы:

- **«No such file or directory»** — устройство переехало на другой
  `/dev/videoN` после переподключения; проверь `ls /dev/video*`.
- **RTSP не открывается в VLC** — проверь, что ffmpeg реально запущен
  (статус в панели) и MediaMTX активен.
- **Сильный лаг** — снизь разрешение/битрейт или включи MJPEG.
