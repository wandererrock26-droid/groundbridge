# Модель лицензирования GroundBridge (набросок)

Документ описывает двухветочную модель распространения GroundBridge:
свободное ядро (OSS) и коммерческая ветка с активацией по ключам. Это
рабочий набросок — юридические формулировки перед реальной коммерцией стоит
показать юристу.

## 1. Две ветки

### OSS-ветка (свободная, замороженная)
- Всё, что уже опубликовано под **GPL-3.0** (текущая версия и ранее).
- Остаётся свободной **навсегда**: GPL-3.0 необратима для уже выпущенного
  кода — тот, кто получил его, сохраняет право использовать, изменять и
  распространять.
- Развитие OSS-ветки замораживается на текущей точке (можно принимать
  мелкие багфиксы, но крупные новые фичи туда не идут).
- Активации не имеет и иметь не может: GPL требует давать исходники и
  разрешать распространение, что несовместимо с аппаратной блокировкой.

### Коммерческая ветка (проприетарная, с активацией)
- Новый код новых версий под **отдельной проприетарной лицензией**
  (черновик — `LICENSE-COMMERCIAL.md`), НЕ под GPL.
- Требует ключ активации, привязанный к конкретной Raspberry Pi.
- Живёт в **приватном** репозитории; публичный остаётся витриной.

### Почему это законно
Ты — **единственный автор и правообладатель**. Правообладатель не связан
собственной GPL-лицензией и вправе выпускать новые версии под любой другой
лицензией (это называется dual-licensing; так делают многие проекты).
Важные границы:
- нельзя «отозвать» GPL у уже розданного кода — старые копии остаются
  свободными;
- нельзя одновременно называть закрытую ветку GPL-3.0;
- если в код попадут чужие правки под GPL (чей-то PR) — их нельзя закрыть
  без разрешения авторов. Вывод: **не принимай чужие PR в коммерческую
  ветку** без CLA (соглашения о передаче прав), иначе потеряешь право
  закрывать код.

## 2. Активация по ключам

### Отпечаток устройства
К каждой малинке привязывается «отпечаток» — SHA-256 от
`серийный_номер_Pi : machine-id` (см. `bridge/license/fingerprint.py`).
Пользователю показывается короткая форма `XXXX-XXXX-XXXX-XXXX`.

Серийник Pi зашит в кристалл и не меняется; machine-id пересоздаётся при
де-клонировании. Поэтому порядок для нового устройства: **сначала
де-клонировать, потом активировать** — ключ привязывается к финальному
machine-id.

### Криптомодель (Ed25519)
- У автора — **приватный ключ** (`groundbridge_license_private.key`,
  в `.gitignore`, никогда не в репозитории).
- В продукт встроен только **публичный ключ** (`bridge/license/verify.py`) —
  им можно лишь проверять подпись, не создавать ключи.
- Ключ активации = base32 от `payload + подпись`, где payload содержит:
  отпечаток устройства, редакцию, дату выпуска, срок действия (или
  бессрочно), метку владельца.
- Проверка на устройстве: подпись валидна публичным ключом → отпечаток
  совпадает → срок не истёк. Подделать ключ без приватного ключа
  невозможно; перенести на другую малинку — тоже (отпечаток не совпадёт).

### Выпуск ключа (сторона автора)
```bash
# пользователь присылает отпечаток из панели (экран активации) или:
python3 -m bridge.license.fingerprint_cli

# автор выпускает ключ:
python3 tools/license_gen.py --priv groundbridge_license_private.key \
    --fp 1A2B-3C4D-5E6F-7A8B --edition pro --customer "БОГОМОЛ #007"
# бессрочный; для срочного: --days 365
```
Готовый ключ пользователь вставляет в панели (экран активации) → он
сохраняется в `data/license.key`, сервис перезапускается уже с полным
функционалом.

### Поведение без валидного ключа (режим блокировки)
При `licensing.enabled: true` и отсутствии/невалидности ключа:
- мост НЕ запускается (не занимает UART/USB/UDP), видео и ZeroTier тоже;
- веб-панель поднимается в режиме активации: показывает отпечаток и поле
  для ключа, весь остальной API закрыт (403).

OSS-ветка: `licensing.enabled: false` — активация не требуется, поведение
не меняется.

## 3. Модель угроз (честно)
Активация выполняется на железе пользователя, поэтому это **барьер, а не
неломаемая DRM**:
- ✅ надёжно защищает от подделки ключей и переноса ключа на другую малинку
  (криптоподпись + привязка к железу);
- ✅ отсекает бытовое «скопировал SD-карту — раздал знакомым»;
- ⚠️ не защищает от того, кто редактирует исходный код и вырезает проверку
  (в коммерческой ветке код закрыт, но при утечке исходников это возможно).
Для повышения планки в будущем: распространять только `.pyc`/собранные
артефакты, обфускация, перенос части логики в подписанный бинарник. На
текущем этапе достаточно подписи ключей + закрытого репозитория.

## 4. GitHub: витрина + приватный репозиторий
У публичного репозитория GitHub нет режима «видно, но нельзя скачать» —
public всегда клонируется. Поэтому:
- **Публичный репозиторий** = витрина: README со скриншотами, описание
  возможностей, документация без исходников (или только замороженная
  OSS-версия). Проект видно, он выглядит солидно.
- **Приватный репозиторий** = активная разработка коммерческой ветки,
  доступ только у тебя и доверенных лиц.

Реализация «временно закрыть скачивание, оставив видимость»: см.
`docs/github-visibility.md`.

## 5. Редакции (задел на будущее)
Поле `edition` в ключе позволяет позже ввести уровни (например `pro`,
`trial`, `lite`) и включать/выключать функции по редакции. Сейчас
используется только метка; тонкую градацию функций добавим, когда
понадобится.
