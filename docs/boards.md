# Одна сборка на три платы: Pi 5, Pi 4 и ROCK 5C

Отдельной версии под каждую плату нет. Станция определяет железо при старте
и подставляет своё: карту UART, номера пинов в подсказках, способ включения
оверлея, источник температуры, работу с вентилятором. Поэтому любая новая
функция появляется на всех платах одновременно — синхронизировать нечего.

Определение живёт в `bridge/platform.py`, паспорт железа снимается скриптом
`tools/hw_report.sh`, а логика установщика проверяется без железа:
`tools/test_platform.py` и `tools/test_install_logic.sh`.

## Главное для распайки

**Провод идёт на один и тот же пин на всех трёх платах.** Это не совпадение,
которое нам повезло найти, а то, ради чего выбирался UART: `uart2` на Pi 5,
`uart3` на Pi 4 и `uart4-m2` на ROCK 5C выведены на **пины 7 и 29**
40-контактной гребёнки.

Практический вывод: переносишь машину с Pi 5 на Pi 4 или на ROCK 5C — паять
заново не нужно, меняется только строчка в конфигурации загрузчика, и её
ставит установщик сам.

Распайка на плату НРТК, одинаковая для всех плат:

- `TXD` → пин **7** (TX выбранного UART);
- `GND` → пин **6** (подойдёт любой GND-пин гребёнки).

Как найти их на гребёнке: **нечётные пины идут одним рядом, чётные —
другим**, счёт начинается от пина 1. Пин 7 — четвёртый в нечётном ряду,
пин 6 — третий в чётном. Ориентир, не зависящий от того, как повёрнута
плата: контактная площадка пина 1 обычно квадратная, у остальных круглая.
Схема с подсвеченными пинами есть прямо в панели, в блоке «Как подключить».

## Что различается

| | Raspberry Pi 5 | Raspberry Pi 4 | Radxa ROCK 5C |
|---|---|---|---|
| SoC / контроллеры UART | BCM2712, UART в RP1 | BCM2711, PL011 | RK3588S2, DesignWare 8250 |
| Оверлей для CRSF | `uart2` | `uart3` | `rk3588-uart4-m2` |
| Как включается | `dtoverlay=` в `config.txt` | `dtoverlay=` в `config.txt` | файл в `/boot/dtbo` + `u-boot-update` |
| Устройство | `/dev/ttyAMA2` | `/dev/ttyAMA3`\* | `/dev/ttyS4` |
| Пины распайки | **7 и 29** | **7 и 29** | **7 и 29** |
| Второй UART (SBUS) | `uart3` → пины 24/21 | `uart4` → пины 24/21 | `rk3588-uart6-m1` → пины 21/19 |
| Управляемый вентилятор | есть (штатный) | обычно нет | есть (`pwm-fan`) |
| Аппаратный H.264 | **нет**, только libx264 | есть, `h264_v4l2m2m` | есть, Rockchip MPP |
| WiFi | встроен | встроен | модуль AIC8800 на USB, драйвер из DKMS |
| `vcgencmd` | есть | есть | нет, температура из `/sys/class/thermal` |

\* Имя устройства на Pi 4 зависит от того, в каком порядке включены
overlay, — об этом ниже.

## Почему именам `/dev/tty*` нельзя доверять

Ядро нумерует устройства в порядке включения overlay. На двух Pi 4 с разным
набором `dtoverlay` один и тот же `ttyAMA2` окажется разными UART. Поэтому
панель имя устройства игнорирует: она читает адрес контроллера в
device-tree и определяет номер UART однозначно.

Адреса PL011 у BCM2711 (Pi 4):

| Адрес | UART | GPIO | Физические пины |
|---|---|---|---|
| `7e201000` | uart0 | 14 / 15 | 8 / 10 |
| `7e201400` | uart2 | 0 / 1 | 27 / 28 |
| `7e201600` | uart3 | 4 / 5 | **7 / 29** |
| `7e201800` | uart4 | 8 / 9 | 24 / 21 |
| `7e201a00` | uart5 | 12 / 13 | 32 / 33 |
| `7e215040` | mini-UART | 14 / 15 | 8 / 10 (это `/dev/ttyS0`) |

Адреса UART у RK3588/RK3588S (ROCK 5C) — uart0 в PMU-домене, дальше ровный
шаг `0x10000`:

| Адрес | UART | | Адрес | UART |
|---|---|---|---|---|
| `fd890000` | uart0 | | `feb90000` | uart6 |
| `feb40000` | uart1 | | `feba0000` | uart7 |
| `feb50000` | uart2 | | `febb0000` | uart8 |
| `feb60000` | uart3 | | `febc0000` | uart9 |
| `feb70000` | **uart4** (пины 7/29) | | | |
| `feb80000` | uart5 | | | |

Таблица сверена с `aliases serial0..serial9` на живой ROCK 5C. Если
определить не удалось, панель так и пишет — и не выдумывает номер пина.

## Включение UART на Radxa

У Radxa нет `config.txt`. Все оверлеи лежат готовыми в `/boot/dtbo` с
суффиксом `.disabled`; включение — снять суффикс и перегенерировать
загрузочный конфиг:

```bash
sudo mv /boot/dtbo/rk3588-uart4-m2.dtbo.disabled /boot/dtbo/rk3588-uart4-m2.dtbo
sudo u-boot-update
sudo reboot
```

Ровно это делает `rsetup` в своём меню (Overlays → Manage overlays →
Enable UART4-M2), только через TUI. Установщик делает это сам, без меню.

Проверить, что оверлей действительно подключён к загрузке:

```bash
grep fdtoverlays /boot/extlinux/extlinux.conf
```

Отладочная консоль Radxa живёт на отдельном `ttyFIQ0` и нашему порту не
мешает — отключать её, в отличие от Raspberry, не нужно.

## Скорость CRSF: проверено на всех трёх платах

CRSF требует нестандартных 420000 бод (или 400000 для TX-модуля), и это
первое, на чём обычно спотыкаются на новом SoC.

| Плата | Запрошено | Ядро выставило | Кадров прошло |
|---|---|---|---|
| Pi 4 Model B Rev 1.5, ядро 6.18 | 420000 | ровно 420000 | — |
| ROCK 5C, Debian 12, ядро 6.1.84 | 420000 | ровно 420000 | 300/300 |
| ROCK 5C | 400000 | ровно 400000 | 300/300 |
| ROCK 5C | 115200 | ровно 115200 | 300/300 |

На RK3588 был обоснованный риск: у Rockchip есть известная проблема
клокового драйвера («fractional div is not allowed»), а расчёт по
регистру дробного делителя обещал для 420000 отклонение около 0.25 %.
На живой плате драйвер `8250_dw` попал точно, отклонения нет вообще.

Проверить у себя (порт подставь свой):

```bash
cd ~/roverlink && source venv/bin/activate
./tools/hw_report.sh /dev/ttyS4
deactivate
```

Скрипт читает реальную скорость из `termios2` через ioctl, а не то, что у
драйвера попросили. Кстати, `stty` для такой проверки не годится: он умеет
только стандартный список скоростей и отвергнет 420000 ещё до обращения к
железу — это ограничение утилиты, а не порта.

Полная проверка с петлёй (перемычка между пинами 7 и 29) гоняет настоящие
CRSF-кадры и считает потери — именно ею подтверждались цифры в таблице:

```bash
sudo python3 tools/uart_loopback_test.py /dev/ttyS4 --frames 300
```

Кадры не абстрактные: адрес `0xC8`, тип `0x16`, 16 каналов по 11 бит,
CRC8 DVB-S2 — те же, что станция отдаёт на ESP32. Зависимостей у скрипта
нет, venv для него не нужен.

## Если в конфиге чужой порт

Типичная ситуация: `config.yaml` приехал с Pi 5 на другую плату, и в нём
остался `/dev/ttyAMA2`, которого здесь нет. Панель это ловит: блок «Как
подключить» желтеет и прямо называет поднятый UART, который надо вписать.
Если поднято несколько UART, панель предлагает тот, что сидит на штатных
пинах 7/29, а остальные просто перечисляет.

Свежую установку установщик настраивает сам, но если правишь руками:

```bash
cd ~/roverlink
sed -i '0,/^\s*port:.*$/s##  port: "/dev/ttyS4"#' config.yaml
sudo systemctl restart roverlink
```

Какой порт у тебя на самом деле — покажет `./tools/hw_report.sh`.

## Вентилятор и температура

У Pi 5 и ROCK 5C есть управляемый вентилятор, и панель им управляет: в обоих
случаях это `cooling_device` типа `pwm-fan`, так что код один. У Pi 4
управляемого вентилятора обычно нет — блок в «Системе» покажет, что
устройство недоступно.

Важная тонкость: наличие `cooling_device` означает, что в системе есть
**управление** вентилятором, а не то, что вентилятор физически воткнут в
разъём. На ROCK 5C узел `pwm-fan` присутствует в device-tree всегда. Поэтому
панель не говорит «работает» по факту существования устройства: при
`cur_state 0` она пишет «остановлен», а если ядро задало ненулевую скорость,
но тахометр показывает 0 оборотов — «не вращается» и предлагает проверить,
подключён ли вентилятор.

Температура читается на всех платах, но по-разному: у Raspberry через
`vcgencmd`, у Rockchip из `/sys/class/thermal`. У RK3588 термозон семь
(soc, bigcore0/1, littlecore, center, gpu, npu) — панель берёт `soc-thermal`
как общую температуру кристалла.

Следить за температурой на Pi 4 стоит внимательнее: без обдува плата в
простое держит около 50 °C, а под нагрузкой видео уходит к троттлингу.

## WiFi на ROCK 5C

У Raspberry адаптер встроен и работает сразу. У ROCK 5C беспроводной модуль
**AIC8800 подключён по USB**, и в минимальных образах (CLI) его драйвер не
собран: прошивка на месте, пакет `aic8800-usb-dkms` стоит, а модуля в
`/lib/modules` нет — DKMS не собрал его без заголовков ядра. Интерфейса
`wlan0` в системе при этом нет вообще, и точку доступа поднимать не на чем.

Установщик это чинит сам, но если делать руками:

```bash
sudo apt install -y linux-headers-$(uname -r) dkms aic8800-usb-dkms
sudo dkms autoinstall -k $(uname -r)
sudo modprobe aic_load_fw_usb
sudo modprobe aic8800_fdrv_usb
```

Модули названы с суффиксом `_usb` — это частая ловушка: `modprobe
aic8800_fdrv` без суффикса не найдёт ничего.

Чтобы драйвер поднимался после перезагрузки:

```bash
printf 'aic_load_fw_usb\naic8800_fdrv_usb\n' | sudo tee /etc/modules-load.d/roverlink-aic8800.conf
```

Режим точки доступа адаптер поддерживает — проверено:
`iw list | grep -A 12 'Supported interface modes'` показывает `* AP`.

### Антенна на ROCK 5C — обязательна

**На плате антенны нет.** Есть только разъём u.FL рядом с беспроводным
модулем, и внешнюю антенну надо прикрутить физически. Без неё всё
выглядит рабочим и не работает:

- `nmcli` пишет, что профиль активен, и назначает `10.42.0.1`;
- `iw dev wlan0 info` показывает `type AP`, выбранный канал и `txpower 18 dBm`;
- `dnsmasq` поднимается и раздаёт пул адресов;
- запущенный вручную `hostapd` рапортует `AP-ENABLED`;
- панель показывает «активна: roverlink»;
- **а телефон и ноутбук сети не видят.**

Заподозрить в такой картине железо почти невозможно — все программные
показания идеальны. Поэтому установщик перед настройкой точки доступа
сканирует эфир: если в жилой застройке не видно **ни одной** чужой сети,
он громко предупреждает про антенну. Ноль сетей при живом драйвере
означает именно оторванный радиотракт.

Проверить руками (интерфейс должен быть в клиентском режиме, в режиме AP
сканирование всегда возвращает пустоту):

```bash
sudo nmcli device wifi list
```

Пусто — антенна. Видны соседи — радиотракт живой.

Ещё одна ловушка рядом: после экспериментов с `hostapd` интерфейс
остаётся `unmanaged` и в режиме `AP`, и тогда `nmcli connection up` падает
с «No suitable device found», а сканирование ничего не находит. Возврат:

```bash
sudo nmcli device set wlan0 managed yes
sudo ip link set wlan0 down && sudo iw dev wlan0 set type managed
sudo ip link set wlan0 up
```

И про регуляторный домен: у AIC8800 строка `phy#0 (self-managed)` — драйвер
ведёт свой домен сам, `iw reg set` на него не влияет. Так что `country 00`
в выводе `iw reg get` на этой плате не является проблемой и искать причину
надо не там.

## Мелочи, на которых спотыкаешься один раз

**`/usr/sbin` нет в `PATH`.** В Debian у обычного пользователя `iw`,
`rfkill`, `dkms` и `u-boot-update` «не находятся», хотя стоят в системе. На
Raspberry Pi OS этой проблемы нет. Установщик и `hw_report.sh` добавляют
`/usr/sbin` в `PATH` сами.

**В CLI-образе нет `unzip`, `git` и `rsync`.** Мы раздаём проект
zip-архивом, а распаковать его на голом Radxa OS нечем. Установщик ставит
эти пакеты первым делом, но сам архив надо чем-то развернуть:

```bash
python3 -m zipfile -e roverlink.zip .
```

**Нет батарейки RTC.** Часы после выключения сбрасываются, из-за чего
`apt` может ругаться на сертификаты, а логи станции получают неверные метки
времени. Лечится один раз: `sudo timedatectl set-ntp true`.

## Видео

У Pi 4 есть аппаратный кодировщик H.264 (`h264_v4l2m2m`, устройства
`/dev/video10`–`video12`), у Pi 5 его нет вообще, у ROCK 5C есть Rockchip
MPP (`/dev/mpp_service`, `/dev/rga`, `/dev/video-enc0`).

Сейчас станция на всех платах кодирует программно. Аппаратное кодирование —
отдельная задача на каждой плате: у `h264_v4l2m2m` свои требования к
форматам пикселей, а `h264_rkmpp` вообще отсутствует в стоковом ffmpeg из
Debian и требует сборки из репозитория Radxa.

В выводе `hw_report.sh` рядом с настоящими кодеками могут стоять
`h264_nvenc`, `h264_vaapi`, `h264_vulkan` — это заглушки из общей сборки
ffmpeg для Debian, на этих платах они не работают.

## Плата не опознана

Если модель не распозналась, станция работает как раньше: ничего не
ломается, просто подсказки по пинам не показываются, а установщик берёт
значения как для Pi 5 и предупреждает об этом. Оверлей в таком случае
задаётся вручную:

```bash
./install.sh --uart uartN
```

## Добавить свою плату

Профили лежат в `_PROFILES` в `bridge/platform.py`: вендор, карта UART с
физическими пинами, таблица адресов контроллеров, способ включения оверлея,
термозона, вентилятор, кодек. Установщик читает те же значения из своего
`case` по device-tree.

Порядок правильный такой: снять `tools/hw_report.sh`, проверить 420000 бод
петлёй, и только потом добавлять профиль. Плата без проверки на живом
железе в таблицу поддержанных не попадает — непроверенный профиль хуже
отсутствующего, потому что создаёт ложную уверенность.
